> 数据库：MySQL 8.0.23（本机 127.0.0.1:3306，账号 trae）

## 一、总览

| 核查维度 | 结论 |
|---|---|

| 数据内容 | `fj_id_card_relation` 自定义关系生产缺失；统计表口径不同 |

## 四、表结构差异（重要）

### 1. `fj_id_card`：派生列为生成列 vs 普通列

生产库 5 个派生列由身份证号**自动计算（STORED GENERATED）**，测试库为**普通可写列**：

| 列 | 生产库 | 测试库 | 生成规则（生产） |
|---|---|---|---|
| `card_len` | GENERATED STORED | 普通列 | `length(card_no)` |
| `region_code` | GENERATED STORED | 普通列 | `substr(card_no,1,6)` |
| `birth_date_str` | GENERATED STORED | 普通列 | 15/18 位解析出生日期 YYYYMMDD |
| `gender_code` | GENERATED STORED | 普通列 | 性别位取模 2 |
| `birth_mmdd` | GENERATED STORED | 普通列 | 出生月日 MMDD |

> ⚠️ 含义：生产库这 5 列**不允许人工写入、由数据库保证派生数据正确**；测试库可任意写入，派生数据可能存在与身份证号不一致的脏数据。测试库看板/视图口径与生产可能因此不一致。

### 2. 自增主键缺失

| 表.列 | 生产库 | 测试库 |
|---|---|---|
| `cdsgus.id` | `int NOT NULL AUTO_INCREMENT` ✅ | `int NOT NULL` ❌ 无自增（注释却写“自增主键ID”） |
| `fj_constellation.id` | `int NOT NULL AUTO_INCREMENT` ✅ | `int NOT NULL` ❌ 无自增 |

> ⚠️ 测试库对这两张表执行不带 id 的 INSERT 会报错（无默认值），需显式传 id，存在插入冲突风险。

### 3. 列注释差异

- `cdsgus`：生产库 30+ 列**注释全部为空**，测试库有完整中文注释 → 两张表来源/创建版本不一致，生产库疑似由更早期无注释版本迁移。
- 视图 `v_fj_id_card_info` 列注释：生产空、测试有（如 户籍地址/邮箱）。
- `fj_constellation` 各表 `TABLE_COMMENT`：生产简短、测试详细（如 `星座表` vs `星座字典表:…`）。

## 五、索引差异（重要）

| 表 | 生产库索引 | 测试库索引 |
|---|---|---|
| `fj_admin_region` | PRIMARY(region_code) | **无任何索引（无主键）** |
| `fj_constellation` | PRIMARY(id)、idx_constellation_range(start_mmdd,end_mmdd) | **无任何索引（无主键）** |
| `fj_mobile_segment` | PRIMARY(segment)、idx_carrier、idx_province | **无任何索引（无主键）** |
| `cdsgus` | PRIMARY + index_ctfid/mobile/name | ✅ 一致 |
| `fj_id_card` | PRIMARY + 6 个索引 | ✅ 一致 |
| `fj_id_card_relation` | PRIMARY + uk_relation_label | ✅ 一致 |
| `fj_id_card_stats` | PRIMARY(dim,bucket) | ✅ 一致 |

> ⚠️ 测试库 3 张字典表（行政区划/星座/手机号段）完全没有索引，看板 JOIN 时会全表扫描；且无主键违反 InnoDB 建表规范（实际会以隐藏 ROWID 作为聚簇索引）。

## 八、数据内容差异

### 1. `fj_id_card_relation`（关系字典）

| value | 生产库 | 测试库 |
|---|---|---|
| -3 客户2 | ❌ 无 | ✅ 有（自定义, 2026-08-27 建） |
| -2 客户1 | ❌ 无 | ✅ 有（自定义, 2026-08-27 建） |
| 0~5 内置关系 | ✅ 有（2026-08-28 重建） | ✅ 有（2026-08-27 建） |

> ⚠️ 生产库缺失测试库中的两个**自定义关系**（客户1/客户2）。若生产库曾定义过这些自定义关系，说明已被重建丢失；若从未定义，则测试库属于超前数据。

### 2. `fj_id_card_stats`（看板预聚合统计）

- 生产库统计覆盖**历史登记年份 1900 / 2010–2013**，基于 ~1860 万人聚合；
- 测试库统计覆盖 **2020–2025**，基于 999 人聚合。
- 两边维度桶数差异巨大（如 surname 生产 3902 vs 测试 213），由数据规模决定，属预期差异；但登记年份分布完全不同，说明**测试数据为新造数据，生产为历史真实数据**。

## 九、风险与建议

1. **生产库自定义关系（客户1/客户2）丢失风险**：确认生产库是否应该包含这两个自定义关系，如需同步需手动补录。
2. **测试库索引缺失**：建议对 `fj_admin_region`、`fj_constellation`、`fj_mobile_segment` 补建主键与业务索引，避免看板全表扫描并符合 InnoDB 规范。
3. **测试库自增列缺失**：建议为 `cdsgus.id`、`fj_constellation.id` 补 `AUTO_INCREMENT`，否则 INSERT 易失败。
4. **`fj_id_card` 派生列口径不一致**：测试库若用手工/脚本写入派生列，需保证与生产生成列规则一致（出生日期/性别/区域由身份证解析），否则看板与视图结果失真。
5. **生产库列注释丢失**：若需要统一文档化，可基于测试库的注释结构对生产库补充 COMMENT（需评估生产变更窗口）。
6. **生产库 6 张历史导入表**：测试库如需复现历史场景，可考虑按需同步结构（无需全量数据）。
